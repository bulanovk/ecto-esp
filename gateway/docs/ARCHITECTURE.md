# Архитектура esp32-gw1

Один UART, две разные скорости на одной паре проводов, один приёмопередатчик.

```
  realPort  — настоящий uart: (GPIO17/16, DE=GPIO23), скорость задаётся драйверу
  intPort   — baud_router: прокси-порт, который хаб видит как UARTComponent
    └── intBus (role: client, turnaround_time 50ms, send_wait_time 1000ms)
          ├── intController — DTSU666,  slave 0x3 @ 9600
          └── r1 (0x1), b2 (0x2), b1 (0x4) — адаптеры бойлеров и реле @ 19200
```

Скорость переключается **в момент отправки кадра**, внутри `BaudRouter::write_array()`:
первый байт кадра — это адрес slave'а, по нему прокси выбирает скорость и, если
она отличается от текущей скорости живого порта, делает `set_baud_rate` +
`load_settings(false)` **перед** записью байт. Кадр уходит целиком на своей скорости.
Никаких окон, скриптов и расписаний: хаб видит один обычный UART и просто
опрашивает всех подряд, а скорость под каждым кадром подставляется сама.

## Почему это безопасно

Проверено по исходникам ESPHome 2026.9.0.

1. `waiting_for_response_` ставится **после** `write_array()`, а `tx_blocked()` его
   учитывает => следующий кадр не будет выбран, пока ответ на текущий не принят
   или не истёк `send_wait_time`. В линии всегда ровно один кадр — это гарантия
   кода, а не оценка таймингов.

2. Пауза между кадрами (`frame_delay_us_` = 3.5 символа) считается **один раз**, в
   `Modbus::setup()`, из геттеров того `UARTComponent`, который ему дали. Значит она
   берётся из `baud_rate` прокси, и прокси **обязан** держать его равным **минимуму
   парка** (9600). Если поставить 19200, пауза станет короче 3.5 символов на
   9600-устройстве и кадры DTSU666 начнут склеиваться. Проверяется автоматически
   в `_validate_routes`.

3. Смена скорости = снос и переустановка драйвера (`load_settings`). Свежее
   RX-кольцо само отбрасывает байты, принятые на старой скорости, — отдельная
   очистка не нужна.

4. DE-пин живёт на `uart:` (аппаратный RS485 half-duplex), а **не** на `modbus:`:
   при software-DE хаб опускает линию сразу после `write_array()`, а прокси в этот
   момент ещё держит кадр в драйвере. Аппаратный режим направление держит сам.

## Что сделать руками, кроме прошивки

a) В Home Assistant **выключить** интеграцию `ectocontrol_adapter` для устройств 1, 2 и 4.
   Два мастера на одной паре проводов будут конфликтовать.

b) Проверить порядок бит реле. Раскладка взята из `docs/PROTOCOL.md` §6.4 репозитория
   [ec-adapter](https://github.com/bulanovk/ec-adapter) (регистр
   0x0010, устройства 0xC0/0xC1) — **не путать** с §6.2: там у contact splitter (0x59)
   тот же адрес 0x0010, но это **другое** устройство с прямой нумерацией битов от 0.
   На железе не проверялась. Переключить «Relay 1» и посмотреть `r1_relay_mask_raw`:
   ожидается 0x0100 (каналы 1-8 = биты 8-15, каналы 9-10 = биты 0-1).

c) Таймеры реле (регистры 0x0020..0x0029) сознательно не поддержаны — вне объёма задачи.

## Объём

Только опрос. У группы B — по одному регистру чтения на устройство, этого достаточно,
чтобы убедиться, что переключение скорости работает. Остальные регистры добавляются по
мере надобности: общий блок 0x0010..0x0023 читается одним кадром, поэтому расширять
список дёшево.

## Сброс «залипших» значений

У Modbus-устройств — автоматизации `on_offline` у контроллеров: публикуют NAN, и
сенсор в HA становится «Неизвестно».

Механизм именно такой, а не через `missing_state`: `Sensor::internal_send_state_to_frontend`
**безусловно** ставит `has_state(true)`, поэтому `missing_state` в API остаётся `false`.
«Неизвестно» получается на стороне HA — `native_value` отбрасывает не-конечные значения.

У BLE-термометров аналога `on_offline` нет (термометр не адресуется), поэтому там стоит
фильтр `timeout: 5min` — см. `templates/ble-thermometer.yaml`.

## Разбиение конфига

Точка входа — `esp32-gw1.yaml`; она содержит только базу (esphome/wifi/api/ota) и список
пакетов. Дальше см. комментарий в её шапке.

## Развёртывание через Device Builder

Конфиг **не копируется** в `/config/esphome/`. Device Builder подключает его как
remote-пакет прямо из этого репозитория — файл `/config/esphome/esp32-gw1.yaml`
состоит из одного блока:

```yaml
packages:
  gw:
    url: https://github.com/bulanovk/ecto-esp
    ref: main
    files: [gateway/esp32-gw1.yaml]
    refresh: always
```

Почему так:

- **Один источник истины.** `external_components` (type: git) тянет **свой отдельный
  клон** того же репозитория — в `.esphome/external_components/`, независимо от
  пакетов в `.esphome/packages/`. Если конфиг лежит в `/config/esphome/` руками, а
  компоненты приезжают из git, получаются две расходящиеся версии: правка YAML в UI
  не меняет компоненты, а `refresh` обновляет только клон. С remote-пакетом и
  конфиг, и компоненты берутся из одного репозитория.
- **Секреты не уезжают в публичный репозиторий.** `!secret` из remote-пакета
  резолвится в каталоге **потребителя** (проверено), то есть в `/config/esphome/secrets.yaml`
  на стороне HA. В репозитории `gateway/secrets.yaml` лежит под `.gitignore`.
- **Репозиторий публичный** — HA клонирует его анонимно, токен не нужен.

Цена: редактировать конфиг из веб-редактора Device Builder нельзя — файлы живут в
клоне репозитория и перезаписываются при `refresh`. Правки идут через git.

### Предусловия

1. В `/config/esphome/secrets.yaml` должны быть три ключа — **настоящие**:

   | Ключ | Где используется |
   |---|---|
   | `wifi_ssid` | `wifi:` |
   | `wifi_password` | `wifi:` |
   | `esp32-gw1_api_key` | `api.encryption.key` |

   Имя ключа API — с префиксом по имени устройства, потому что `secrets.yaml`
   общий на все устройства: голое `api_key` заставило бы их делить один ключ.
   Следующее устройство получает `<device>_api_key`.

   В репозитории лежат заглушки `test-ssid` / `test-password`; ключ API там
   записан настоящим, но берётся он не из репозитория, а из secrets потребителя.
   **Ключ обязателен:** без него сборка упадёт с «Secret 'esp32-gw1_api_key' not
   defined». Значение должно совпадать с тем, что HA уже знает для этого
   устройства — иначе связь с API не установится и устройство придётся удалять
   и добавлять в HA заново.
2. Порядок действий: сначала `git push` этого репозитория (Device Builder читает
   `ref: main`, локальные коммиты ему не видны), потом добавление устройства в UI.
3. `external_components` и пакет клонируются раздельно. Если правился **код
   компонентов**, одного `refresh` пакета мало — нужен перезапуск сборки или чистка
   `.esphome/external_components/` в контейнере Device Builder.
